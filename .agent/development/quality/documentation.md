# 文档同步规范

## 核心约束

> 任何新增或变更用户可感知模块的开发，都必须同步更新对应引导文档；没有可执行引导和验收步骤的功能，不视为完成。

这是一条完成定义，不是发布后的补充任务。功能关闭、重命名、延期或出现新限制时，也必须同步文档。

## 哪些变化必须更新文档

- 新增或修改模块能力、配置、CLI、HTTP API、AppModule Schema。
- 改变安装依赖、编译命令、运行方式、错误信息或安全要求。
- 改变数据库行为、数据版本、兼容性、迁移或恢复方式。
- 新增示例 AppModule、Provider 或部署组合。
- 修改用户在快速开始中可以观察到的输出。

完全不改变外部行为、构建、配置和运维语义的内部重构可以豁免，但 Pull Request 必须写明判断依据。

## 每个模块指南的固定内容

`docs/modules/<module>.md` 至少包含：

1. 用途和适用场景。
2. 当前实现状态，明确区分“已实现”和“计划”。
3. 前置条件。
4. 最短可运行示例。
5. 配置项、默认值和安全提示。
6. 非专业用户可以重复执行的验收步骤。
7. 常见错误和恢复方式。
8. 当前限制。
9. 兼容或升级影响。

可以从[模块指南模板](./module-guide-template)开始。

## 开发流程

1. 开始新模块时，先复制模板并登记 `docs/_meta/modules.json`。
2. 定义功能验收时，同时写模块的用户验收步骤。
3. 实现过程中保持命令、配置和示例输出与代码一致。
4. 修改快速开始涉及的行为时，同步更新 `docs/getting-started/` 和 README。
5. 完成前由未参与实现的人按文档走一遍 Golden Path。
6. 执行 `make docs-check` 和模块清单中的 acceptance 命令。

## 自动检查

`scripts/check-docs.mjs` 会验证：

- 基础入门页面是否存在。
- 模块清单中的源码路径和指南是否存在。
- 每个模块指南是否包含必需章节。
- 每个 `examples/modules/` 示例是否已经登记。
- 模块是否给出至少一个验收命令。

VitePress 构建继续检查 Markdown 渲染和内部链接。CI 使用 Node.js 22 与 lockfile 执行同样检查。

```sh
make docs-setup
make docs-check
```

自动检查只能减少漏项，不能证明文字正确。实际命令和预期结果仍须人工或端到端测试验证。

## 写作体验要求

- 新手页面优先使用“运行方式、模型版本指纹、数据空间”等通俗表达，专业术语随后说明。
- 每组命令写明在哪个终端、哪个目录运行。
- 每个关键步骤写出可观察的成功标志。
- 危险操作使用显著警告，并提供安全默认方案。
- 不把未来计划写成当前能力，不把 UI Schema 描述成可视化 Manager。
- 不依赖外部字体、登录态或云端搜索，保证内网可读。

## 文档系统决策

Panvara 使用 VitePress 1.x 稳定版：源文件保持普通 Markdown，默认中文，内置本地搜索，支持响应式布局、暗色模式和未来 `/en/` 多语言目录。Node 只用于文档构建，不进入 Go 运行时。

alpha 阶段不复制版本化文档树。出现第二个需要并行维护的稳定大版本后，再引入 `/v1/`、`/v2/` 和版本选择器；每次发布应先保存对应静态文档制品。
